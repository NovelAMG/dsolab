Three layers. Code lives on your laptop. Pushed to GitHub. GitHub creates things in Azure on your behalf. That's the whole flow.

Why bother with GitHub creating things — why not just click in the portal?

This is the key idea behind DevOps. Three reasons:

  1. Repeatable — if you click in the portal, no one else can repeat exactly what you did. With code in GitHub, anyone (or any robot) can recreate the same setup with one command.
  2. Reviewable — every change is a "pull request" (PR). You see exactly what's about to change before it changes. Like a security review, but for infrastructure.
  3. Audit-able — git log shows every change ever made, who made it, when, and why. Same as audit logs, but for cloud config.

The cost: you have to learn the developer tooling (git, terraform, gh). That's what these phases are teaching you.

The critical concept: GitHub Actions doesn't have Azure permissions on its own. It can only do things in Azure as the Managed Identity. The MI is what's authorized — GitHub Actions just borrows its identity for ~10 minutes per workflow run, using a cryptographic handshake called OIDC (no passwords ever).

Bootstrap vs Terraform — the two setup phases

This is the part everyone gets confused about. There are two kinds of setup:

flowchart LR subgraph PHASE_A["Phase A: Bootstrap — you, by hand, ONCE"] B1[Run scripts/00-bootstrap-state.sh] B2[Creates: state storage,
GHA managed identity,
RBAC role assignments] B3[Sets: GitHub repo variables
so workflows know who to login as] B1 --> B2 --> B3 end subgraph PHASE_B["Phase B: Terraform — the robot, EVERY change"] T1[You edit a .tf file] T2[git push → PR → merge] T3[GitHub Actions runs terraform apply] T4[Creates: AKS, ACR, KV,
AOAI, Postgres, etc.] T1 --> T2 --> T3 --> T4 end PHASE_A -->|enables| PHASE_B

Bootstrap = "Build the trust foundation so the robot can take over." You do this once, manually, because:

  • You need an Azure account first (chicken-and-egg — Terraform can't create the identity it logs in as).
  • You need a place to store Terraform's state file (chicken-and-egg again — Terraform can't store its own state without a place that already exists).
  • These are one-time setup items that never change.

Terraform = "The robot's job description." Everything else lives here. AKS, ACR, Key Vault, Postgres, OpenAI, role assignments between them, network rules — all written as code in .tf files. The robot reads the code and makes Azure match.

What is Terraform doing, in 4 words?

"Make reality match code."

That's it. You write .tf files saying "I want an AKS cluster called this, with 2 nodes of size Standard_B2s, in southeastasia." Terraform:

  1. Reads your .tf files → knows what you want ("desired state").
  2. Reads Azure → knows what's already there ("actual state").
  3. Diffs the two → produces a "plan" listing every change needed.
  4. Applies the plan → calls Azure APIs to create / modify / delete until actual = desired.

It's like a security baseline scanner. But instead of just reporting drift, it fixes it automatically.

What is GitHub Actions doing, in 1 sentence?

"When code changes, run this script."

Each .yml file in .github/workflows/ is a recipe. When a trigger happens (push, PR, schedule), GitHub runs the recipe on a fresh VM. Recipes we have:

WorkflowTriggerWhat it does
hello-world.ymlManual or when itself changesLogs into Azure, prints subscription info. Proves OIDC works.
tf-plan.ymlAny PR touching terraform/Runs terraform plan (read-only), posts result as a comment on the PR
tf-apply.ymlMerge to main touching terraform/Runs terraform apply (actually makes changes in Azure)

Let's trace what happened when you ran gh pr merge 3 to fix the KV admin issue:

No passwords, no secrets, no manual portal clicks. That's the whole DevOps win.

Why this is more secure, not less

A security person's instinct: "But running scripts in GitHub on my Azure is scary." Actually it's the opposite. Compare:

Old way (click in portal)DevOps way (this lab)
Permissions held by humans → human leaves company, perms might survive Permissions held by an identity scoped to one repo. Repo deleted = identity becomes useless
Changes have no audit trail beyond Azure activity log Every change has a git commit, a PR, a reviewer, a timestamp, a reason
Drift between dev/staging/prod is normal Drift is forbidden — TF re-asserts desired state every run
Secrets stored in keyvaults, accessed by passwords No passwords anywhere. OIDC + workload identity from day 1
Security review = "ask the team what they did" Security review = "read the PR diff"

Dev workflow cheatsheet — the commands you'll see in every runbook

You will see the same 6–8 command shapes over and over. Once you can read these, runbooks stop being scary.

Git — the time machine + branching

CommandWhat it does (plain English)
git checkout main"Move me to the main branch." Like switching to a different tab.
git pull"Download any commits other people pushed to this branch since I last looked."
git checkout -b feat/04-cluster-prereqs"Create a NEW branch called feat/04-cluster-prereqs off whatever branch I'm on, and switch to it." The -b means "branch, please make it."
git add ."Stage everything I changed in this folder (and below)." Staging = "include this in the next commit." The . means "current dir + everything under it."
git commit -m "feat(1cd): adr 0001 + identity module""Save a snapshot of staged changes with this message." The -m is just shorthand for "give me a message inline so you don't open a text editor."
git push -u origin feat/04-..."Upload my branch to GitHub." origin = the GitHub copy. -u = "and remember this so next time I can just type git push."
gh pr create --fill"Open a pull request on GitHub using my commit message as the description."
gh pr merge 4 --squash --delete-branch"Merge PR #4 by squashing all my commits into one tidy commit, then delete the feature branch."

Why branches? So broken WIP code never touches main. main is "what the robot will deploy." Branches are "your scratchpad."

Terraform — describe infra, then apply

CommandWhat it does
terraform initDownloads providers (azurerm, azuread) and connects to the state file in Azure Storage. Run once per checkout.
terraform plan"Show me a diff: what would you change if I said yes?" READ-ONLY. Always run before apply.
terraform applyActually makes the changes. Will re-run plan and ask you to type yes.
terraform outputPrint values the modules exposed (e.g., AKS OIDC issuer URL).

We rarely run these locally — GitHub Actions runs them for us when a PR is opened (plan) and when it merges (apply).

Azure CLI (az) — talk to Azure from your laptop

PatternWhat it does
az loginOpens a browser, asks you to sign in. After this, every az command runs as you.
az account show"Which subscription am I currently pointed at?"
az aks get-credentials -g RG -n CLUSTERWrites a ~/.kube/config entry so kubectl can talk to this AKS cluster.
az aks start / stopPowers the cluster on/off. Stopping saves money but breaks anything that talks to it.
az role assignment create --assignee X --role Y --scope Z"Give identity X the role Y on resource Z." This is how RBAC works.
... --query "..." -o tsvThe --query uses JMESPath (a JSON query language) to pick a field; -o tsv prints it raw (no quotes), perfect for assigning to a shell variable.

Kubectl — talk to Kubernetes

CommandWhat it does
kubectl get nodesList the VMs in the cluster. "Ready" = healthy.
kubectl get pods -n n8nList pods in the n8n namespace. -n = namespace (think: folder).
kubectl apply -f file.yaml"Make Kubernetes match what's in this YAML file." Creates or updates as needed.
kubectl logs pod-name -n n8nPrint stdout/stderr from a container. Add -f to follow live.
kubectl describe pod X -n n8nLong-form info: events, conditions, image pull errors. First stop when something's broken.
kubectl get svc -n ingress-nginxList services. For LoadBalancer services, this is how you find your public IP.

Helm — Kubernetes package manager

CommandWhat it does
helm repo add NAME URL"Remember this chart repository under this short name."
helm repo update"Refresh the index of all known repos." Run before installing.
helm install RELEASE_NAME REPO/CHART -n NAMESPACE"Install this chart with this nickname into this namespace." A chart = a bundle of K8s YAML templates.
helm upgrade --install ... Install if missing, upgrade if exists. Idempotent — safe to re-run.
helm list -A"What did I install, across all namespaces?"

Shell glue you'll keep seeing

PatternMeaning
VAR=$(some command)Run the command, capture its stdout into VAR.
"$VAR"Use VAR's value. The quotes prevent spaces from breaking things.
cmd1 && cmd2Run cmd2 only if cmd1 succeeded. Chains things safely.
cmd | tail -5Run cmd, but only show the last 5 lines. | = "pipe output into next command."
cmd 2>&1Combine error output into normal output (so grep can see it).
cd /path/to/dir && ...Switch to that directory first, then run the rest. Doesn't permanently change your shell.

Why we ran into trouble (the 3 errors of yesterday)

All 3 errors had the same root cause: the MI's permissions and Terraform's view of reality got out of sync. Now you have the mental model to understand exactly what each was:

ErrorPlain English
Plan failed with "register RP"Terraform tried to register Azure features at subscription level. Our MI is only RG-level. Fix: register them by hand (you, as Owner) and tell Terraform to skip auto-registration.
Apply failed with "RoleAssignmentExists 409"Terraform tried to create a role assignment, but a duplicate one was already there from yesterday's manual fix. Terraform can't see things it doesn't manage.
Apply failed with "cluster not in Running state"AKS was stopped (cost-saving). Terraform tried to update it. Azure refuses updates while stopped. Fix: start AKS before applying.

All three are classic DevOps lessons. You hit them in 24 hours of real work. Most people learn these over months. You're ahead.

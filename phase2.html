1. TL;DR

Build-time security = automated scanners that read code/config/images before they ever deploy. We added five of them. They run on GitHub's servers every time someone proposes a change. If they find something serious, the change cannot be merged. Findings appear in one dashboard at github.com/<repo>/security.

You don't run them manually. They run themselves when triggered by a code change.

2. The mental model: build-time vs runtime

Security splits into two halves. Phase 2 is the left half. Phase 3 will add the right half.

Build-time scanners look at the artifact before it ships. "This Terraform file would create a public storage bucket — don't merge it." They cannot tell you what's actually running in your cluster right now. That's Phase 3's job.

The key insight: most production breaches start with something that could have been caught at build time — hardcoded creds, outdated library with a CVE, misconfigured S3 bucket, weak Dockerfile. Fixing it before merge is cheap. Fixing it after deploy means an incident.

3. What CI/CD actually is (no jargon)

CI = Continuous Integration. Every time someone commits code, automated checks run.
CD = Continuous Deployment. If checks pass, the change gets deployed automatically.

GitHub's implementation is called GitHub Actions. The pieces:

WordWhat it actually means
WorkflowA YAML file in .github/workflows/. Like a shell script with a schedule.
Trigger (on:)The event that starts it. Examples: someone pushed to main, someone opened a PR, a cron schedule fired.
JobA group of steps that run together on one fresh virtual machine (a "runner").
StepOne command or one prebuilt action. E.g. "checkout the code", "run Trivy".
ActionA reusable pre-packaged step published by someone (Microsoft, Aqua, etc.). You reference it by name + version like aquasecurity/trivy-action@v0.36.0.
RunnerThe throwaway Ubuntu/Windows/macOS VM where your workflow runs. Lives for the duration of one job, then dies.
SARIFA standard JSON format for "here are the security findings I found". CodeQL, Trivy, Checkov all emit SARIF; GitHub's Security tab consumes it.
Analogy: A workflow file is a recipe. The trigger is when to cook ("on Sunday mornings", "when someone rings the doorbell"). The runner is the kitchen. The job is the dish. The steps are the instructions.

4. The "when X happens, run Y" pattern

Every workflow is shaped like this: 

name: Trivy (image scan)        # Display name in GitHub UI

on:                              # ← TRIGGER (the X)
  pull_request:
    branches: [main]
    paths:
      - 'spa/**'                 #   only when SPA files change in a PR

permissions:                     # What this workflow is allowed to touch
  contents: read
  security-events: write         # upload findings to Security tab

jobs:                            # ← THE Y (what to do)
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4              # get the code
      - uses: docker/build-push-action@v6      # build the image
      - uses: aquasecurity/trivy-action@v0.36  # scan it
        with:
          exit-code: '1'         # ← fail the job if it finds anything HIGH/CRITICAL

That's the whole pattern. Every one of our workflows follows it. Different trigger, different steps, same shape.

6. All 7 of our workflows, one by one

These are exactly what appears in your screenshot of github.com/.../actions.

BLOCKING — failure stops merge INFORMATIONAL — failure surfaces but does not stop merge DEPLOY — not a check, it makes changes

1. Hello World (OIDC smoke test) utility, not security

File.github/workflows/hello-world.yml TriggerManual click ("Run workflow") or when the file itself changes What it doesLogs into Azure using OIDC (no passwords), prints subscription info, exits Why existsProves the GitHub ↔ Azure trust relationship works. If this fails, nothing else that touches Azure will work either. Relates to PRNo — it's a manual diagnostic tool

2. Terraform Plan (PR) infrastructure preview

File.github/workflows/tf-plan.yml TriggerAny PR that touches terraform/** What it doesRuns terraform plan — a dry-run that says "if you merged this, here's what would change in Azure". Posts the diff as a comment on the PR. Why existsSo reviewers can see "this PR would delete a Key Vault" before approving. No surprises post-merge. Relates to PRYes — its output appears as a comment on every infrastructure PR

3. Terraform Apply (main) DEPLOYS to Azure

File.github/workflows/tf-apply.yml TriggerPush to main that touches terraform/** (i.e. immediately after a TF PR merges) What it doesRuns terraform apply — actually makes the changes in Azure that the PR described. Why existsThis is GitOps. The git history IS the deployment record. To change Azure, you open a PR; merging it deploys it. Relates to PRRuns after the PR is merged. Not a gate. It's the deploy step.

4. CodeQL (SAST) source code scanner

File.github/workflows/codeql.yml TriggerPR or push to main touching spa/**, plus weekly cron What it doesReads the SPA TypeScript looking for security bug patterns: hardcoded secrets, XSS sinks, weak crypto, prototype pollution, etc. Uploads findings as SARIF. Why existsCatches "the developer wrote insecure code" — not a CVE in a library, but a mistake in our own source. Free for public repos via GitHub. Relates to PRYes — appears as a check; findings appear in the Security tab and inline on the PR diff

5. Trivy (image scan) BLOCKING on HIGH/CRITICAL

File.github/workflows/trivy-image.yml TriggerPR or push to main touching spa/**, plus weekly cron What it doesBuilds the SPA container image (exactly as it would be deployed), then scans every OS package and npm dependency inside it against CVE databases. Fails the build if any fixable HIGH/CRITICAL exists. Why existsThe image is what actually runs in production. If nginx:alpine ships with a Log4j-style CVE, we know before deploy, not after. Relates to PRYes — and it BLOCKS the merge if a critical CVE is found

6. Checkov (IaC) misconfiguration scanner

File.github/workflows/checkov.yml TriggerPR or push to main touching terraform/**, k8s/**, or spa/Dockerfile What it doesParses your Terraform, K8s YAML, and Dockerfile. Runs ~1000 rules looking for misconfigurations: public storage, weak TLS, no encryption, root containers, no resource limits, etc. Uploads SARIF to Security tab. Why existsCatches "the engineer wrote infrastructure that's insecure". E.g. a TF file that creates an Azure Storage account with public-blob access — Checkov flags it before it deploys. Relates to PRYes — INFORMATIONAL right now (~95 inherited findings being triaged in issue #17). Will be BLOCKING once the baseline is clean.

7. Dependabot Updates opens PRs for you

File.github/dependabot.yml (not a workflow file — config for a GitHub-built-in bot) TriggerWeekly schedule + instantly when a new CVE matching your deps drops What it doesReads package.json, GitHub Actions versions, Terraform providers, Docker base images. Opens PRs that bump them. Why existsSoftware rots. Yesterday's safe library has today's CVE. Dependabot does the version-bumping work for you and makes the bump a normal PR that runs all your checks. Relates to PRDependabot IS a PR opener. The PRs it opens then go through CodeQL/Trivy/Checkov like any other PR.
The pattern: 2 of these (Plan, Apply) are for deploying infrastructure. 4 of these (CodeQL, Trivy, Checkov, Dependabot) are for security. 1 (Hello World) is a diagnostic. Each one has a single job: trigger + steps + result.

7. How this connects to Pull Requests

A Pull Request (PR) is "I propose this change to the codebase, please review and merge". Every workflow with on: pull_request appears as a check on the PR. GitHub shows them at the bottom of the PR page as a list of green/red boxes.

sequenceDiagram participant Dev as Engineer participant Git as GitHub (repo) participant CI as GitHub Actions (runners) participant Sec as Security tab Dev->>Git: git push (new branch) Dev->>Git: open Pull Request Note over Git,CI: GitHub sees the PR, checks each workflow's "on:" trigger Git->>CI: PR touches spa/** → run CodeQL + Trivy Git->>CI: PR touches terraform/** → run TF Plan + Checkov CI-->>Git: post results as "checks" on the PR CI-->>Sec: upload findings as SARIF alt Any blocking check failed Git-->>Dev: Merge button DISABLED Dev->>Git: push fix (or accept finding) Note over Git,CI: checks re-run automatically else All checks green Git-->>Dev: Merge button enabled Dev->>Git: click Squash & merge Git->>CI: now run main-only workflows
(TF Apply deploys to Azure) end

The contract: blocking checks must be green before merge. Informational checks just show up; reviewer decides. You never have to run anything by hand — GitHub orchestrates it all when the PR is opened.

8. Concrete scenarios: "I change X, what happens?"

Scenario A — You add an Azure Storage Account to Terraform

You open the file terraform/envs/lab/main.tf and append a public-blob storage account:

resource "azurerm_storage_account" "demo" {
  name                     = "stdemo123"
  resource_group_name      = azurerm_resource_group.lab.name
  location                 = "southeastasia"
  account_tier             = "Standard"
  account_replication_type = "LRS"
  allow_nested_items_to_be_public = true   # ← Checkov will flag this
}

You commit, push, open a PR. This is what happens automatically within ~2 minutes:

GitHubSees the PR. Looks at each on: trigger. Notices terraform/** changed.
tf-plan.ymlRuns terraform plan. Posts a comment on your PR: "+ 1 resource (azurerm_storage_account.demo)". So reviewers can see the diff in human terms.
checkov.ymlParses the same file. Hits rule CKV_AZURE_59 ("Ensure that Storage Accounts disallow public access"). Uploads SARIF. Today: shows up in Security tab (informational). Soon: blocks the PR.
codeql.ymlDoesn't run — you didn't touch spa/**.
trivy-image.ymlDoesn't run — same reason.
YouSee a red Checkov finding on the PR. Either fix it (allow_nested_items_to_be_public = false) or — if there's a good reason — add an allow-list entry to .checkov.yaml with a written reason.
After mergetf-apply.yml runs automatically. terraform apply creates the storage account in Azure.
Before Phase 2: that storage account would have been created in Azure, sat there publicly, and waited to be exploited or noticed weeks later.
After Phase 2: the engineer sees the finding in the PR within 2 minutes, fixes it, and the public bucket never exists.

Scenario B — You upgrade the SPA's React version

You edit spa/package.json from "react": "^18.3.1" to "react": "^19.0.0" and push.

codeql.ymlRuns (SPA changed). Re-analyses TS — catches anything that became newly invalid under React 19's typings.
trivy-image.ymlRuns. Builds a fresh image with new deps. Scans. Reports any CVEs in the new dep tree.
checkov.ymlDoesn't run — no IaC changed.
tf-plan.ymlDoesn't run.
YouSee 2 green checks. If a CVE shows up, react@19.0.1 might already have it fixed — bump again, push, checks re-run.

Scenario C — Dependabot opens a PR for you (no human action)

It's Monday morning. A new CVE in vite drops. Dependabot sees you depend on a vulnerable version.

DependabotOpens PR #N: "Bump vite from 5.4.10 to 5.4.12". Title prefixed chore(spa-deps):.
codeql.ymlRuns (PR touches spa/**).
trivy-image.ymlRuns. The new vite version is clean — Trivy passes. (Before the bump it would have failed.)
YouLook at the PR. All checks green. Click Merge. Done.
This loop is what "shift-left" means in practice. The CVE was disclosed at 09:00. Dependabot opened a PR at 09:05. Checks ran by 09:08. You merged at 09:10. Total exposure window: minutes, not weeks.

Scenario D — You try to commit an API key by accident

You're testing locally, paste a real Azure key into a file, run git push.

GitHub (push protection)The push is REJECTED at the server before the commit lands. You see:
remote: error: GH013: Repository rule violations found for refs/heads/...
remote: - Push cannot contain secrets.
YouRemove the key, push again. Or, if it's a false positive, click the link GitHub gave you to mark it as allowed.

This isn't a workflow at all — it's GitHub's secret-scanning + push-protection feature. It's already on for your repo. No code, no YAML, you just benefit from it.

10. One-page cheatsheet

QuestionAnswer
Where do workflows live?.github/workflows/*.yml — one YAML file per workflow.
Where does Dependabot config live?.github/dependabot.yml — single file, lists which ecosystems to watch.
How do they get triggered?The on: block at the top: push, pull_request, schedule (cron), or workflow_dispatch (manual).
Where do they run?On a fresh Ubuntu VM ("runner") that GitHub provides. Free for public repos.
How do findings reach the dashboard?Each scanner outputs SARIF (a standard JSON). The upload-sarif action pushes it to GitHub. Security tab consumes it.
Who decides what blocks a PR?The workflow itself, via exit codes. exit-code: '1' = fails the check = blocks the PR (if branch protection is on).
Why are some scans "informational"?Because the baseline has known findings we haven't fixed yet. Blocking from day 1 would freeze the repo. Flip to blocking once baseline is clean.
Is this GitHub Advanced Security?Yes — and on a public repo it's free. On a private repo, GHAS is a paid line item.
Do I have to write YAML?You don't. Your engineers do (once, then it runs forever). You read the Security tab.
What if a finding is a false positive?Dismiss it in the UI with a reason ("False positive — N/A in lab"), OR add to .checkov.yaml skip-list with a comment. Either way, the rationale is preserved.
Bottom line for a security engineer: The YAML is the engineer's responsibility — they write it once. Your job is to (a) make sure all five scanners exist and run, (b) check the Security tab regularly, (c) triage findings into "fix" or "accept-with-reason", and (d) flip informational scanners to blocking once the baseline is green. That's Phase 2 done.

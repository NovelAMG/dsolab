DevSecOps Lab — Hands-on demo plan

Become the Junior Dev: Phase 2 in action

You've watched the engineer (me) build all this. Now you sit in their chair. You make changes. You push. You watch the gates fire — or block you. Six 10-minute scenarios that make every Phase 2 concept concrete.

Scenarios (do them in order — each builds on the previous)
  1. Prep — set up your local dev machine (one-time)
  2. Demo 1 — Try to push directly to main (and fail) easy · 5 min
  3. Demo 2 — Add a public Azure storage account in Terraform easy · 10 min
  4. Demo 3 — Try to commit a fake API key (push protection blocks you) easy · 5 min
  5. Demo 4 — Introduce a known-vulnerable npm package medium · 15 min
  6. Demo 5 — Watch Dependabot open a PR while you sleep easy · 5 min active
  7. Demo 6 — Triage a Security tab finding (Checkov) medium · 10 min
  8. Cleanup — close any test PRs / revert test branches
  9. Final takeaways

0. Prep — set up your local dev machine

One-time setup so you can actually open PRs from your laptop.

What you need installed:
  • git — comes with macOS Xcode CLI tools (xcode-select --install)
  • gh — GitHub CLI (brew install gh)
  • VS Code (you have this) or any editor
1

Authenticate the GitHub CLI. Run this once and follow the browser flow:

gh auth login

Pick: GitHub.com → HTTPS → Yes (authenticate Git) → Login with a web browser. Paste the device code.

2

You already have the repo cloned. Just make sure you're on main and up to date:

cd ~/Desktop/DevSecOps-True
git checkout main
git pull origin main
3

Confirm you can see the workflows that will run:

ls .github/workflows/
Expected: seven files: checkov.yml, codeql.yml, hello-world.yml, tf-apply.yml, tf-plan.yml, trivy-image.yml, plus dependabot.yml in the parent .github/ folder.
Workflow for every demo below: always create a branch (git checkout -b demo/something), make a change, commit, push, open PR, watch checks, then close or merge. You'll never push to main directly — that's what Demo 1 proves.

Demo 1 — Try to push directly to main (and fail)

What you're learning: branch protection. The reason every change has to go through a PR.

Demo 1 · The branch protection rule in action

easy · 5 min
1

On main, make a tiny edit. Add a blank line to README.md:

git checkout main
echo "" >> README.md
git add README.md
git commit -m "test: try to push to main"
2

Try to push:

git push origin main
Expected: GitHub rejects with: 
! [remote rejected] main -> main (protected branch hook declined)
error: failed to push some refs
That's branch protection saying "no direct pushes to main, you must use a PR".
3

Undo your local commit (it's not on GitHub anyway):

git reset --hard origin/main
What you just saw: the rule we set up earlier (gh api PUT .../branches/main/protection) actually stops the most common foot-gun in DevOps: someone (you, me, a script) pushing untested code straight to production.

Demo 2 — Add a public Azure storage account (Checkov catches it)

What you're learning: IaC scanning. You'll write Terraform that creates an insecure resource, open a PR, and watch Checkov flag it before it ever deploys.

Demo 2 · A misconfigured storage account never reaches Azure

easy · 10 min
1

Create a branch:

git checkout main
git pull origin main
git checkout -b demo/insecure-storage
2

Create a new file terraform/envs/lab/demo_storage.tf with this content:

resource "azurerm_storage_account" "demo" {
  name                     = "stdemoinsecure123"
  resource_group_name      = "rg-dsolab-sea"
  location                 = "southeastasia"
  account_tier             = "Standard"
  account_replication_type = "LRS"

  # ↓↓↓ THIS is the insecure part — Checkov will flag it
  allow_nested_items_to_be_public = true
}

Save in VS Code.

3

Commit and push:

git add terraform/envs/lab/demo_storage.tf
git commit -m "demo: insecure storage account (intentional for testing)"
git push -u origin demo/insecure-storage
4

Open a PR from the command line:

gh pr create --base main --head demo/insecure-storage \
  --title "demo: insecure storage account" \
  --body "Intentionally insecure for Phase 2 demo."

Output prints the PR URL. Open it in the browser.

5

Wait ~2 minutes for the checks to appear at the bottom of the PR page.

Expected checks (in order of appearance):
  • Terraform Plan (PR) — runs terraform plan and posts a comment on the PR showing what would change
  • Checkov scan — runs and uploads SARIF; today this is INFORMATIONAL so the check goes green (we haven't flipped Checkov to blocking yet — see issue #17)
  • CodeQL and Trivy do not run — you didn't touch spa/**
6

Open the Security tab to find your new finding:

open "https://github.com/tonzking123/dsolab/security/code-scanning?query=tool%3Acheckov+is%3Aopen"
What you'll see: a new finding like CKV_AZURE_59 — Ensure that Storage Accounts disallow public access pointing to terraform/envs/lab/demo_storage.tf line 9. Click it to see the rule explanation, severity, and remediation guidance.
7

Two options here. As a security person, decide which is realistic:

  • Option A (recommended): fix the finding. Edit the file, change true → false, commit, push. Checks re-run; the Security tab finding will auto-close once the new commit is scanned.
  • Option B: accept the finding with a reason. In the GitHub UI on the finding page, click "Dismiss" → choose a reason ("Used in tests", "Won't fix", "False positive"). That's audit-logged.
8

Don't merge this PR. Close it without merging — it was just for the demo:

gh pr close --delete-branch <pr-number>
What you just saw: a misconfigured cloud resource was caught before Terraform Apply could create it in Azure. In the "before Phase 2" world, this would have shipped to prod and waited to be exploited. With Checkov, you see it in 2 minutes on the PR — the cheapest possible moment to fix it.

Demo 3 — Try to commit a fake API key (push protection blocks you)

What you're learning: secret scanning + push protection. The instant feedback when you accidentally paste a credential.

Demo 3 · Push protection slams the door

easy · 5 min
1

Create a branch:

git checkout main && git pull
git checkout -b demo/leaked-key
2

Create a file leak.txt with a fake but valid-looking GitHub token (the format triggers the scanner; the value is fake):

echo "GITHUB_TOKEN=ghp_AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA" > leak.txt
git add leak.txt
git commit -m "demo: leak a token"
3

Try to push:

git push -u origin demo/leaked-key
Expected: GitHub rejects the push with a message like: 
remote: error: GH013: Repository rule violations found
remote: Push cannot contain secrets
remote: — GITHUB PERSONAL ACCESS TOKEN —
remote:     locations:
remote:       - commit: <sha>
remote:         path: leak.txt:1
remote:     We recommend you remove or replace the secret with a placeholder.
! [remote rejected] demo/leaked-key -> demo/leaked-key (push declined due to repository rule violations)
The commit never reaches GitHub. No history rewriting needed.
4

Clean up locally — delete the file and the commit:

git reset --hard HEAD~1
rm -f leak.txt
git checkout main
git branch -D demo/leaked-key
What you just saw: the most common breach root-cause (developer commits a secret) prevented at the network boundary — the secret literally never left your laptop. This is one toggle in GitHub settings, free for public repos.

If you ever need to push something that looks like a secret but is intentionally a sample/placeholder, GitHub gives you a one-time bypass URL in the error message.

Demo 4 — Introduce a known-vulnerable npm package

What you're learning: SCA (Software Composition Analysis) via Dependabot + Trivy. CVE detection in third-party code.

Demo 4 · A vulnerable dep can't slip past Trivy

medium · 15 min
Pick a package carefully. We need something with a public, fixable HIGH/CRITICAL CVE that the SPA wouldn't realistically use in production. lodash@4.17.4 is a classic: known prototype pollution CVE-2019-10744 (HIGH), the package itself is harmless.
1

Branch + add the vulnerable dep:

git checkout main && git pull
git checkout -b demo/vulnerable-lodash
cd spa
npm install lodash@4.17.4 --save
cd ..

This modifies both spa/package.json and spa/package-lock.json.

2

Commit and push:

git add spa/package.json spa/package-lock.json
git commit -m "demo: add vulnerable lodash for testing"
git push -u origin demo/vulnerable-lodash
gh pr create --base main --head demo/vulnerable-lodash \
  --title "demo: vulnerable lodash" \
  --body "Intentionally pulls in CVE-2019-10744 for Phase 2 demo."
3

Wait ~3 minutes and look at the PR checks.

Expected:
  • CodeQL (Analyze) — runs; will probably pass (lodash's vuln is a usage pattern, not your code)
  • Build SPA + Trivy scan — RED. Trivy builds your SPA image with the new dep tree, sees lodash@4.17.4, matches it against the CVE database, and fails the gate because it's HIGH severity and fixable.
  • Checkov, TF Plan — don't run; no relevant files changed
The Merge button is greyed out for the Trivy check.
4

Click the Trivy check → "Details" to see the actual finding in the workflow log. You'll see the CVE ID, severity, package, and the fixed version.

What to look for in the log: a line like lodash 4.17.4 CVE-2019-10744 HIGH (fixed in 4.17.12).
5

Now fix it. Bump to a clean version:

cd spa
npm install lodash@latest --save
cd ..
git add spa/package.json spa/package-lock.json
git commit -m "fix: bump lodash to clean version"
git push

Checks re-run automatically. Trivy passes this time. Merge button enables.

6

Close the demo PR (don't merge; we don't actually want lodash in the repo):

gh pr close --delete-branch <pr-number>
What you just saw: a fixable HIGH CVE in a third-party library blocked at the PR. Trivy compared the package version against the National Vulnerability Database in seconds. No human had to remember to check.

This is exactly what Dependabot does too — Demo 5 shows the same loop but initiated by the bot, not by you.

Demo 5 — Watch Dependabot open a PR while you sleep

What you're learning: the automated half. Dependabot watches your package.json and opens PRs without you doing anything.

Demo 5 · Dependabot is your overnight intern

easy · 5 min active (but you wait for the bot)
Reality: Dependabot is already running. The first PRs will appear within 24 hours of the .github/dependabot.yml being merged (yesterday for you). You don't have to wait — you can manually trigger a check.
1

Force Dependabot to look right now:

open "https://github.com/tonzking123/dsolab/network/updates"

This is the Dependabot dashboard. Each ecosystem (npm, terraform, github-actions, docker) shows its last-scan time and any pending updates.

2

Click any "Last checked" row → "Check for updates now". GitHub will scan in ~30 seconds and open PRs if anything is out of date.

3

Look at the PRs list:

gh pr list --author "app/dependabot"
Expected: a list of any Dependabot-opened PRs. Each one is titled like chore(spa-deps): Bump vite from 5.4.10 to 5.4.12.
4

Open one in the browser. Notice what's there:

  • A summary of what changed (version, links to changelog and commit history of the upstream package).
  • The same CI checks run on Dependabot PRs as on your PRs — CodeQL, Trivy, Checkov. The bot's PR has to pass the same gates.
  • If you trust Dependabot's compatibility-score, comment @dependabot merge and the bot will merge it once checks pass.
5

For learning, pick the smallest Dependabot PR (e.g., a patch bump to a dev dep) → merge it via the GitHub UI Merge button (you'll have to be the one to click since you set 0 required approvals; in a real team a second human would approve).

What you just saw: the loop that catches CVEs disclosed at 3am on a Saturday. Dependabot sees them, opens a PR, your CI runs, and Monday morning you either merge or investigate. This is the single most valuable Phase 2 mechanism over time — most security incidents are old known CVEs in transitive deps.

Demo 6 — Triage a Security tab finding (Checkov)

What you're learning: the daily security-engineer workflow. Not pushing code — reading findings, deciding what to do with each one.

Demo 6 · Triage one of the 95 inherited Checkov findings

medium · 10 min
1

Open the Code scanning tab filtered to Checkov:

open "https://github.com/tonzking123/dsolab/security/code-scanning?query=tool%3Acheckov+is%3Aopen"
2

Pick any finding — start with one that looks easy. Good candidates to look for:

  • CKV_AZURE_42 — Ensure the key vault is recoverable (soft-delete) — usually a 1-line TF fix
  • CKV_DOCKER_2 — Ensure that HEALTHCHECK instructions have been added — add one line to spa/Dockerfile
  • CKV_K8S_* — probably needs a securityContext block somewhere
3

Click the finding. Read what it tells you:

  • Rule — what's wrong
  • Severity — how bad
  • Location — exact file and line
  • Description / Remediation — how to fix
  • Compliance frameworks — which standards (CIS, NIST) this maps to
4

Make a decision. Three valid choices, each with a different button:

DecisionHowWhen
Fix itOpen a PR that addresses the rule. When Checkov re-scans on that PR, the finding auto-closes.Real misconfiguration, easy to fix
Dismiss — won't fixClick "Dismiss alert" → reason "Won't fix" + a comment explaining whyLab-only choice, expensive to fix, not worth it
Dismiss — false positiveSame UI, different reasonThe rule misidentified the situation
5

For learning, do one of each. Pick three findings. Fix one, dismiss-wont-fix one, dismiss-false-positive one. Note that each dismissal forces you to type a reason — that reason is what your auditor reads later.

6

Refresh the dashboard. Count is down by 3. Multiply this by 95 over a few weeks and you have a clean baseline. Then you flip Checkov to blocking (per ADR 0015) so no new finding can ever be merged.

What you just saw: this is the actual daily job of a DevSecOps engineer. Not writing YAML — reading findings, deciding "fix / accept / false positive", and documenting the reason. The tools are just there to surface things.

Cleanup

After running the demos, clean up your test branches and PRs so the repo doesn't accumulate junk:

# Close any open demo PRs
gh pr list --author "@me" --search "demo:" --json number --jq '.[].number' | \
  xargs -I {} gh pr close {} --delete-branch

# Delete any local branches starting with demo/
git branch | grep '^  demo/' | xargs -r git branch -D

# Make sure you're back on main
git checkout main && git pull origin main
